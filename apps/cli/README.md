# The MaxPrice Headless client

`maxprice` is the Headless client: MaxPrice with no window, for a Linux server. It tracks this machine's Claude Code usage from its session logs, prints the Desktop client's reports in a terminal, and can join a Hub as a Connected client. It is one binary, for Linux x64 with glibc.

## Install

The Headless client ships as `maxprice_<version>_linux-x64.tar.gz` on the [releases page](https://github.com/meschoening/MaxPrice-Release/releases), starting with the first release that ships it. The tarball holds one file, `maxprice`, with mode 0755. Download it, then, in the directory that holds it and no other `maxprice_` tarball:

```sh
mkdir -p ~/.local/bin && tar -xzf maxprice_*_linux-x64.tar.gz -C ~/.local/bin
```

The same line replaces an older `maxprice` there and leaves the rest of `~/.local/bin` alone. It needs no root. A daemon already running keeps the old version, and the other commands exit 4 until it restarts, so restart it: `systemctl --user restart maxprice` for the user unit. [`maxprice update`](#updating) replaces the binary and restarts the unit in one step.

On Ubuntu and Debian, the default `~/.profile` adds `~/.local/bin` to `PATH` at your next login once the directory exists. Until then, or in a shell that does not, add it yourself:

```sh
export PATH="$HOME/.local/bin:$PATH"
```

Then check that it runs:

```sh
maxprice --version
```

## First run

The daemon, `maxprice serve`, does the work: it reads this machine's Claude Code logs, keeps the Local archive, and answers the commands that need it over a Unix socket in its [data dir](#the-data-dir). Run it in one shell:

```sh
maxprice serve
```

It stays in the foreground and logs to stderr. `[serve] listening on …/daemon.sock` means it is up. In another shell:

```sh
maxprice status
```

`status` prints the daemon's state as a checklist, one line per part. While the first scan runs, its Engine line says so; the reports wait for the scan to end. Then try a report:

```sh
maxprice daily
```

By default the daemon reads `~/.config/claude/projects` and `~/.claude/projects`, or `$CLAUDE_CONFIG_DIR/projects` when `CLAUDE_CONFIG_DIR` is set; `maxprice settings set claude-paths` changes the list. The Usage limits need the claude.ai session key (`maxprice key set`), and other machines' usage needs a Hub (`maxprice hub join`).

Ctrl-C stops `serve` with exit 0, and so does closing its terminal. To keep it running, run it [as a service](#run-it-as-a-service).

## Run it as a service

```sh
maxprice service install
```

This writes a systemd user unit, `~/.config/systemd/user/maxprice.service` (or the user manager's own config home, when it has another), then enables and starts it. The unit's `ExecStart` is the `maxprice` that ran `install`, so run it from the binary the unit should run. Run it again after moving the binary.

A user unit runs while your user manager does, and by default that ends with your last login session. When linger is off, `install` says so and prints the step that keeps the manager running from boot, logged in or not:

```sh
loginctl enable-linger
```

If `loginctl` refuses, an administrator can enable it for you with `sudo loginctl enable-linger <user>`.

The unit `install` writes, for a user `dev`:

```ini
# Generated by `maxprice service install`, which rewrites this file.
# Customize it with `systemctl --user edit maxprice`.
[Unit]
Description=MaxPrice Headless client
StartLimitIntervalSec=15min
StartLimitBurst=5

[Service]
Type=exec
ExecStart=/home/dev/.local/bin/maxprice serve
Restart=on-failure
RestartSec=10s
RestartPreventExitStatus=5 6

[Install]
WantedBy=default.target
```

- **Restarts.** A crash (exit 1) restarts after 10 s. Once five starts fall within 15 minutes, systemd refuses the next and leaves the unit failed; it counts every start, hand restarts and `maxprice update`'s included. Exits 5 and 6 never restart: another `serve` holds the data dir, or `serve` refused its settings.json, and a relaunch fixes neither. `maxprice service install` clears a failed state.
- **Your shell's variables.** The user manager never sees them. When the installing shell sets `CLAUDE_CONFIG_DIR` or `XDG_DATA_HOME`, `install` adds an `Environment=` line for each after `ExecStart`, and prints it. A relative `CLAUDE_CONFIG_DIR` entry is made absolute against the current directory.
- **Customizing.** `install` puts the generated text back whenever the file differs from it, so a hand edit is lost, and it never touches the unit's drop-ins: put changes in one with `systemctl --user edit maxprice`. When the file changed, `install` restarts a running daemon.

Day to day, `systemctl --user start|stop|restart maxprice` drives the unit, `maxprice service status` describes it, and `maxprice service logs -f` follows its journal.

The unit needs a systemd user manager, which `systemctl --user` reaches. With none, as in a container or an SSH session with no `XDG_RUNTIME_DIR` or user bus, every `service` verb exits 1 and says so. Run `serve` under another init instead.

## Other inits

`maxprice serve` runs under any supervisor that keeps a process in the foreground.

### A systemd system unit

A system unit runs the daemon for one user, with no user manager and no linger. Write `/etc/systemd/system/maxprice-dev.service`, with `dev` replaced by that user's name:

```ini
[Unit]
Description=MaxPrice Headless client for dev
StartLimitIntervalSec=15min
StartLimitBurst=5

[Service]
Type=exec
User=dev
ExecStart=/home/dev/.local/bin/maxprice serve
Restart=on-failure
RestartSec=10s
RestartPreventExitStatus=5 6

[Install]
WantedBy=multi-user.target
```

Name it `maxprice-<user>.service`, never `maxprice.service`: `maxprice update` takes a daemon running in a `maxprice.service` cgroup for the user unit, and would not tell you to restart it. The name also lets several users run one each.

systemd sets `HOME` from `User=`, so the daemon reads that user's `~/.claude` and keeps its files in that user's `~/.local/share/maxprice`, the data dir that user's own commands reach. When that user's logs or data dir are elsewhere, add `Environment=CLAUDE_CONFIG_DIR=…` or `Environment=XDG_DATA_HOME=…` under `[Service]`, with absolute paths, since a system unit runs in `/`. Then:

```sh
sudo systemctl daemon-reload
sudo systemctl enable --now maxprice-dev
```

It differs from the user unit in four ways:

- `maxprice service …` manages only the user unit. Use `sudo systemctl status|restart|stop maxprice-dev`, and `sudo journalctl -u maxprice-dev` for its logs.
- The hints a command prints when the daemon is down or runs another version name the user unit or a foreground `serve`. Read them as `sudo systemctl … maxprice-dev`, and never also run `maxprice service install`: the two units would contend for one data dir, and the loser stops on exit 5.
- `maxprice update`, run as that user from a shell whose data dir is the unit's, swaps the binary and prints `A 'maxprice serve' (pid N) still runs <old version>: restart it to finish the update.` Restart it with `sudo systemctl restart maxprice-dev`.
- Linger is not needed.

On a host where SELinux is enforcing, as RHEL and Rocky Linux ship, the system manager may be refused a binary under `/home` (`status=203/EXEC` in `systemctl status`). Then install the binary outside `/home`, such as `/usr/local/bin`, and point `ExecStart` there, or use the user unit, which is not affected.

### Any other supervisor

Give `serve` this contract:

| Exit | When                                                                     | The supervisor                                                                                                              |
| ---- | ------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------- |
| 0    | SIGTERM, SIGINT or SIGHUP stopped it cleanly                             | Leaves it stopped                                                                                                           |
| 1    | A crash or a failed bind                                                 | Restarts it after a delay, within a bound: the generated unit waits 10 s, and gives up once 5 starts fall within 15 minutes |
| —    | Killed by a signal the supervisor did not send, such as the OOM killer's | Restarts it, as after exit 1                                                                                                |
| 5    | Another `maxprice serve` holds this data dir                             | Never restarts it                                                                                                           |
| 6    | It refused its settings.json                                             | Never restarts it. Its log says why; fix the file, then start it                                                            |

- Run it as the user whose `~/.claude` it reads, with that user's `HOME`, and with `CLAUDE_CONFIG_DIR` or `XDG_DATA_HOME` when that user's commands set them.
- It stays in the foreground: it never daemonizes and writes no PID file for the supervisor. `serve.lock` holds its pid for its own messages, and keeps it after it exits.
- Stop it with SIGTERM. SIGINT and SIGHUP do the same: once it has logged `listening on`, each runs its teardown and exits 0. Before that, the signal's default action ends it.
- It logs to stderr, and its boot trace to stdout. Keep both.
- One `serve` runs per data dir. A second one exits 5 and leaves the first running.
- It listens on no network port: the other commands reach it over `daemon.sock` in the data dir. It connects out over HTTPS to claude.ai, the LiteLLM price list and the update channel, and to its Hub when one is joined.

## Commands

Every command takes `-h` or `--help`, and `maxprice help <command>` prints the same text. Every command exits 0 when it succeeds; each section's table lists its other codes, and [Exit codes](#exit-codes) lists them all. Errors go to stderr, and stdout carries only the answer, so `--json` output pipes cleanly.

### Report options

`daily`, `sessions` and `projects` take every one of these; `blocks` takes all but `--project`, and `live` only `--org` and `--json`.

| Option             | Meaning                                                                                                           |
| ------------------ | ----------------------------------------------------------------------------------------------------------------- |
| `--since <date>`   | The first day, `YYYYMMDD` or `YYYY-MM-DD`                                                                         |
| `--until <date>`   | The last day, in the same forms. With neither, the range is this week, as the Week setting defines it             |
| `--model <family>` | Only this Model family: Fable, Opus, Sonnet or Haiku                                                              |
| `--project <name>` | Only this project, by its path or its folder name                                                                 |
| `--machine <name>` | Only this machine, by its name, its id or an 8-character id prefix; needs a Hub joined with the Fleet replica on  |
| `--org <org>`      | `all`, `home`, or one Tracked organization by its uuid, an 8-character uuid prefix or its label (default: `home`) |
| `--json`           | Print the daemon's response verbatim                                                                              |

`--model`, `--project` and `--machine` repeat to name more. Days are local dates in the timezone setting, or with none set, the shell's `TZ`.

With `--json`, a report pipes into a tool such as `jq`:

```sh
maxprice daily --since 2026-10-01 --json | jq '.daily[] | {date, totalCost}'
maxprice live --json | jq '.usage'
```

### `maxprice serve`

`maxprice serve`: run the daemon in the foreground, as [First run](#first-run) does. It takes no options.

- It keeps its files in the [data dir](#the-data-dir), tightens that dir to 0700, listens on `daemon.sock` there (0600), and holds a lock on `serve.lock`, so one daemon runs per data dir.
- It reads `settings.json` and refuses to start on a file it cannot read as a JSON object, or one whose Home organization or tracked list is a value the setting does not take. On a first boot it saves the Home organization it chose there.
- It reads `secrets.json` once, at start. It tightens one that group or others can reach to 0600, and skips one it cannot use with one log line; it never exits for that file. A change made by hand applies at the next start.
- It checks the update channel at boot and every 6 hours, writes what it found to `update-check.json`, and never installs anything.
- It logs to stderr, and its boot trace to stdout. SIGTERM, SIGINT and SIGHUP stop it cleanly, with exit 0.

| Exit | Meaning                                                                                                               |
| ---- | --------------------------------------------------------------------------------------------------------------------- |
| 1    | A crash or a failed bind                                                                                              |
| 2    | An option or an argument: `serve` takes none                                                                          |
| 5    | Another `maxprice serve` holds this data dir                                                                          |
| 6    | settings.json cannot be read, or its Home organization or tracked list is rejected; fix the file, then start it again |

### `maxprice service install|uninstall|status|logs`

`maxprice service <verb>`: the daemon as a systemd user unit ([Run it as a service](#run-it-as-a-service)). There is no start, stop or restart verb: `systemctl --user` does those.

- `install` writes the unit, enables it and starts it, as above.
- `uninstall` stops and disables the unit and removes its file. The data dir, its secrets.json, the drop-ins and linger stay.
- `status` shows the unit's state, start time, restarts and last exit; whether it runs this maxprice and serves this shell's data dir; linger; and whether the daemon answers on its socket. The daemon's own state is `maxprice status`.
- `logs` shows the unit's journal, as `journalctl --user --user-unit=maxprice.service` does, and exits with journalctl's own code. `-f` or `--follow` follows it, and `-n <N>` or `--lines <N>` shows the last N lines.

| Exit | Meaning                                                                                                                                                  |
| ---- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1    | No systemd user manager, a systemctl step failed, `journalctl` is not on `PATH`, or `uninstall` found the file gone while the manager still has the unit |
| 2    | A bad verb or option, an argument after the verb, `-f` or `-n` with a verb other than `logs`, or a `-n` that is not a whole number                       |
| 3    | `status`: the unit is inactive, failed or not installed; `logs`: the unit is not installed                                                               |

### `maxprice status`

`maxprice status [--json]`: the daemon's state as a checklist. Daemon (its version and socket), Engine (the scan, a saturated event loop, a stalled watcher, an archive it cannot write), Limits (whether the session key is set, and its age), Hub and Pricing come first; then each Tracked organization's limits once the scan is done, Update (the daemon's last check of the update channel), a Settings line for each value in settings.json the setting does not take, a Secrets line when secrets.json is open to group or others or cannot be used, and the [double-join warning](#a-desktop-client-on-the-same-machine). Each line is marked `✓` ok, `!` warn, `✗` bad or `–` off, and one with a fix names the command for it. No line shows any part of the session key or the Hub password.

Once the daemon answers, `status` exits 0, whatever the marks say. `--json` prints the daemon's `/api/status` answer verbatim. Colour shows only on a terminal, and `NO_COLOR` or `TERM=dumb` turns it off.

| Exit | Meaning                                            |
| ---- | -------------------------------------------------- |
| 1    | A daemon error, a timeout or a bad response        |
| 2    | An option other than `--json`, or an argument      |
| 3    | The daemon is not running                          |
| 4    | The daemon runs another version than this maxprice |

### `maxprice settings get|set|unset`

`maxprice settings get [<setting>]`, `maxprice settings set <setting> <value>...` and `maxprice settings unset <setting>`: show or change this client's settings, kept in `settings.json` in the data dir. `get` shows each value that applies and its source: set in the file, the default, or rejected (the file holds a value the setting does not take, and the default applies). `set` refuses a value the setting does not take with exit 2, writing nothing. `unset` removes the setting from the file, so it follows its default.

| Setting         | Values                                                                                                                                              |
| --------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| `timezone`      | An IANA time zone, such as `Europe/Berlin`. Unset, the shell's `TZ`                                                                                 |
| `cost-mode`     | `auto`, `calculate` or `display`. Unset, `auto`                                                                                                     |
| `week`          | `rolling`, `limit-reset`, or `custom <day> <HH:MM>`, the day `sun` to `sat` and the time on a 24-hour clock. Unset, `rolling`                       |
| `time-format`   | `12h` or `24h`. Unset, the host's                                                                                                                   |
| `claude-paths`  | One or more directories to watch, replacing the list. Unset, `$CLAUDE_CONFIG_DIR/projects`, or `~/.config/claude/projects` and `~/.claude/projects` |
| `share-events`  | `on` or `off`: share this machine's Fleet events with the Hub. Unset, `on`                                                                          |
| `fleet-replica` | `on` or `off`: keep a Fleet replica of the Hub's events. Unset, `on`                                                                                |

The daemon applies `claude-paths`, `share-events` and `fleet-replica` live; when it is not running, the change applies when it starts. The other four apply from the next command on. Each write takes a lock on `settings.lock` and changes only its own setting.

```sh
maxprice settings set week custom mon 09:00
```

| Exit | Meaning                                                                                                                                                                                                      |
| ---- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 1    | settings.json cannot be read or is not a JSON object (it is left as it is), another maxprice held the lock for 5 s, the write failed, or the daemon failed to answer the check (the change is still written) |
| 2    | A bad command, option, setting or value                                                                                                                                                                      |
| 4    | The daemon runs another version than this maxprice; the change is still written                                                                                                                              |

### `maxprice org list|track|exclude|home`

`maxprice org list`, `maxprice org track <org>`, `maxprice org exclude <org> [--confirm <label>]` and `maxprice org home <org>`: list this machine's Organizations, or change which of them it counts. Home and the Tracked organizations are kept in settings.json. Every verb needs the daemon, and first waits for its initial scan.

- `list` shows each Organization, Home first. Its columns are Organization, Id, Tracking (Home, Tracked or Excluded), Current login (a login on this machine names it), Seen on and Re-walking.
- `track` counts an Excluded organization again: its usage is re-walked from the session files into every report.
- `exclude` stops counting a Tracked organization: its usage leaves every report on this machine, and while a Hub is joined, this machine's sessions for it leave the Hub. It prints what it removes, then on a terminal asks you to type the Organization's label. Off a terminal, `--confirm <label>` gives the label instead. There is no `--yes`.
- `home` makes a Tracked organization Home. The old Home stays tracked, so nothing is re-walked.

`<org>` is an Organization's uuid, an 8-character uuid prefix (the Id `org list` prints), or its label, exact and case-sensitive. Home is always tracked: to exclude it, make another Tracked organization Home first. After a change, `org` waits until the daemon shows it and nothing is being re-walked; Ctrl-C stops the wait, and the daemon finishes on its own.

```sh
maxprice org exclude 1a2b3c4d --confirm "Example Research"
```

| Exit | Meaning                                                                                                                                                                                                                                                                     |
| ---- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1    | No Home organization yet; exclude of Home; home of an Organization that is not tracked; a label that does not match; settings.json cannot be read, or its Home or tracked list is rejected (it is left as it is); another maxprice held the lock for 5 s; or a daemon error |
| 2    | A bad command or option, a name that matches no or several Organizations, or exclude off a terminal with no `--confirm`                                                                                                                                                     |
| 3    | The daemon is not running                                                                                                                                                                                                                                                   |
| 4    | The daemon runs another version than this maxprice; nothing is written                                                                                                                                                                                                      |
| 130  | `exclude`: Ctrl-C at the label prompt; nothing is written                                                                                                                                                                                                                   |

### `maxprice key set|clear`

`maxprice key set` and `maxprice key clear`: store or remove the claude.ai session key the daemon reads the Usage limits with. It is kept in `secrets.json` in the data dir, readable by this user alone (0600), and never in settings.json.

- `set` reads the key, checks it with claude.ai through the daemon, stores it, then hands it to the daemon. On a terminal it asks for the key and shows nothing as it is typed or pasted; otherwise it reads all of stdin, as in `maxprice key set < key.txt`. The key is never an argument, since argv lands in shell history and `ps`. It needs the daemon running.
- `clear` removes the stored key, and the daemon's copy when it runs. It needs no daemon.

The key is the `sessionKey` cookie of a browser signed in to claude.ai, a value starting `sk-ant-sid01-`. To copy it from a browser on another machine, open the developer tools at claude.ai, then Application (Chrome, Edge) or Storage (Firefox), Cookies, `https://claude.ai`, and copy the value of `sessionKey`. It is not Claude Code's OAuth token (`sk-ant-oat…`), which `set` refuses; maxprice never reads `~/.claude/.credentials.json`.

Ctrl-C at the prompt exits 130, having stored nothing.

| Exit | Meaning                                                                                                                                                                                                                                |
| ---- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1    | The key is a Claude Code OAuth token, claude.ai refused it or could not be reached, secrets.json cannot be used or written, the daemon did not take the key (it is still stored, for the daemon's next start), or another daemon error |
| 2    | A bad command or option, an argument after `set`, or no key given                                                                                                                                                                      |
| 3    | `set`: the daemon is not running                                                                                                                                                                                                       |
| 4    | The daemon runs another version than this maxprice; for `clear`, the change is still written                                                                                                                                           |
| 130  | `set`: Ctrl-C at the prompt; nothing is stored                                                                                                                                                                                         |

### `maxprice hub join|leave`

`maxprice hub join <url> [--password] [--no-auto-heal]` and `maxprice hub leave`: join this client to a MaxPrice Hub, or leave it. The Hub's URL and auto-heal are kept in settings.json, and its Hub password in secrets.json (0600).

- `join` joins the Hub at `<url>`: a host, `host:port` or a full URL, with `http://` and port 47100 when it names none. The URL cannot carry a username or password. It needs the daemon running, saves the config, hands it to the daemon and waits up to 10 s for the daemon to reach the Hub. Each join writes the URL, the password and auto-heal together, so re-run it to change any one of them.
- `leave` removes the Hub's URL and password, and tells the daemon when it runs. It needs no daemon, and keeps the auto-heal setting.
- `--password`: the Hub has a password. `join` asks for it, showing nothing as it is typed, or with no terminal reads all of stdin. Without it the join is passwordless, and a stored password is removed.
- `--no-auto-heal`: never push this client's session key to the Hub when the Hub's own key stops working. Auto-heal is on without it.

A rejected password, a Hub version mismatch or no answer in 10 s exits 1, with the config still saved; the daemon keeps retrying a Hub that did not answer. While the Desktop client on this machine is joined to a Hub too, `join` [warns](#a-desktop-client-on-the-same-machine). Ctrl-C at the password prompt exits 130, having saved nothing.

```sh
maxprice hub join hub.example:47100 --password
```

| Exit | Meaning                                                                                                                                                                                                                                                                    |
| ---- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1    | The Hub rejected the password, is another version or did not answer in 10 s (the config is saved); another command left the Hub meanwhile; a file cannot be used or written; the daemon did not take the config (it is saved, for the next start); or another daemon error |
| 2    | A bad command or option, a missing or invalid URL, or no password given                                                                                                                                                                                                    |
| 3    | `join`: the daemon is not running                                                                                                                                                                                                                                          |
| 4    | The daemon runs another version than this maxprice; for `leave`, the change is still written                                                                                                                                                                               |
| 130  | `join --password`: Ctrl-C at the prompt; nothing is saved                                                                                                                                                                                                                  |

### `maxprice update`

`maxprice update [--check [--json]]`: install the newest maxprice from the update channel over this binary. `--check` only says whether a newer one is available, exiting 100 when it is and 0 when this one is current; with it, `--json` prints `{"current":…,"latest":…,"available":…}`. [Updating](#updating) says what it checks and what it restarts.

| Exit | Meaning                                                                                                                                                                                    |
| ---- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 1    | The check or the update failed, and this binary is unchanged; or, with this binary already replaced, the restart failed or the restarted daemon did not report the new version within 30 s |
| 2    | Usage error                                                                                                                                                                                |
| 100  | `--check` found a newer maxprice                                                                                                                                                           |

| 2    | More than one command, or an unknown one |

## Exit codes

| Exit | Meaning                                                               |
| ---- | --------------------------------------------------------------------- |
| 0    | Success                                                               |
| 1    | Failure: a daemon error, a timeout, a bad response or a crash         |
| 2    | Usage error                                                           |
| 3    | The daemon is not running                                             |
| 4    | The daemon runs another version than this maxprice                    |
| 5    | Another `maxprice serve` holds this data dir                          |
| 6    | `maxprice serve` refused its settings.json                            |
| 100  | `maxprice update --check` found an update                             |
| 130  | Ctrl-C at a prompt: `key set`, `hub join --password` or `org exclude` |

Nothing is written when a prompt is interrupted. `key set` and `hub join --password` exit 130 themselves; at `org exclude`'s prompt the SIGINT ends the process, which a shell reports as 130 and a supervisor as a signal.

## Updating

```sh
maxprice update --check
maxprice update
```

`update` reads the Headless client's own channel entry, `headless-latest.json`, and installs a release only when it is signed by MaxPrice's key, under its own version, newer than this maxprice, and its binary runs here and prints that version. Anything else leaves this binary as it is. There is no downgrade and no rollback: the previous release stays on its release page. It never runs sudo, so this user must be able to read, write and search the binary's directory, as it can `~/.local/bin`.

After the swap:

- A running `maxprice.service` whose `ExecStart` is this binary is restarted with `systemctl --user restart maxprice.service`, and `update` waits up to 30 s for it to report the new version. If it does not, `update` exits 1 and names `maxprice service logs`.
- A unit that runs another binary is left running, and `update` says so.
- A `maxprice serve` outside the user unit, in a terminal, a [system unit](#a-systemd-system-unit) or another init, is left running, and `update` says to restart it. Until you do, commands exit 4 and name the two versions.
- Run as root, as for a shared `/usr/local/bin`, it restarts nothing: each user restarts their own unit with `systemctl --user restart maxprice`.

The daemon checks the channel at boot and every 6 hours, and never installs anything. `maxprice status`'s Update line shows what it found: `! Update` with `→ maxprice update` when a newer release is out, `✓ Update current`, `– Update check failed` with the reason, or `– Update not checked yet` just after a boot. A failed check is not `✗`, since a server with no route to GitHub is not broken.

## A Desktop client on the same machine

A Desktop client and a Headless client on one machine can both join a Hub. They do not double-count: the Hub keeps one copy of each usage event. But this machine's usage then splits between two Machine directory entries, so the Machine filter misleads. Join only one of them to a Hub.

The Headless client cannot tell whether the Desktop client's Hub is its own, so it warns whenever the Desktop client's settings, `$XDG_DATA_HOME/com.maxprice.desktop/settings.json` (`~/.local/share/com.maxprice.desktop/settings.json` by default), name any Hub: at `maxprice hub join`, as a line in `maxprice status`, and once in the daemon's log at boot. It never blocks.

## The data dir

The data dir is `$XDG_DATA_HOME/maxprice`, or `~/.local/share/maxprice` when `XDG_DATA_HOME` is unset or not absolute. The daemon and every command compute it the same way, so a shell with another `XDG_DATA_HOME` reaches another daemon; `maxprice service status` flags a unit whose data dir is not the shell's. `serve` creates it 0700 and tightens one that group or others can reach, so only this user can open the files in it. Keep it on a local filesystem: its locks, its socket and its SQLite files are unsupported on a network filesystem.

| File                                           | What it holds                                                                                             | Mode                 |
| ---------------------------------------------- | --------------------------------------------------------------------------------------------------------- | -------------------- |
| `daemon.sock`                                  | The daemon's socket, which every other command connects to. The next `serve` removes a stale one          | 0600                 |
| `serve.lock`                                   | The lock that keeps one `serve` per data dir, and the pid of the last `serve` that took it                | 0600                 |
| `settings.json`                                | This client's settings, written by `settings`, `org` and `hub`, and by a first boot's Home                | 0600                 |
| `settings.lock`                                | The lock every settings write takes                                                                       | 0600                 |
| `secrets.json`                                 | The claude.ai session key and the Hub password; there is no file while neither is stored                  | 0600                 |
| `update-check.json`                            | The daemon's last check of the update channel, which `status` shows                                       | 0600                 |
| `machine-id`                                   | This machine's id, minted at its first boot; a Hub knows the machine by it                                | umask                |
| `local-archive.sqlite`, with `-wal` and `-shm` | The Local archive: this machine's own usage events, kept after Claude Code prunes their JSONL             | 0644, less the umask |
| `usage-history.jsonl`                          | The Usage history: the usage-limit samples the daemon took or received from a Hub                         | umask                |
| `scan-cache.json`                              | The parse cache, so a restart re-reads only the JSONL that changed                                        | umask                |
| `pricing-cache.json`                           | The last LiteLLM price list fetched                                                                       | umask                |
| `organizations.json`                           | The Organizations the daemon has seen, with their plans                                                   | umask                |
| `organization-labels.json`                     | The Organization labels                                                                                   | umask                |
| `organization-assertions.json`                 | The Organization assertions                                                                               | umask                |
| `organization-repair.json`                     | The record of the repair a change to the tracked set runs                                                 | umask                |
| `fleet-events.sqlite`, with `-wal` and `-shm`  | The Fleet replica, while a Hub is joined and `fleet-replica` is on; a disposable copy of the Hub's events | 0644, less the umask |
| `fleet-forget.json`                            | A forget on the Hub still in progress, with its receipts, so a lost answer never repeats it               | umask                |
| `machine-directory.json`                       | A copy of the Hub's Machine directory, for machine names while the Hub is away                            | umask                |
| `identity-directory.json`                      | The Identity directory, which folds a project's checkouts across machines                                 | umask                |

A file marked umask has the mode the umask gives a new file. A write to most of these goes through a temporary file beside it, renamed into place. A file the daemon cannot read is kept beside it as `<name>.bak`, and the daemon starts that part empty.

A first boot over Claude Code logs, with no session key and no Hub, writes `daemon.sock`, `serve.lock`, `settings.json` (its Home organization), `settings.lock`, `update-check.json`, `machine-id`, the Local archive, `scan-cache.json`, `organizations.json` and `organization-repair.json`. The others appear with what they hold.

Both the archive reset below and the data deletion in [Uninstalling](#uninstalling) require `realpath` with `-m -s` support (GNU coreutils or a compatible implementation). These options normalize `.` and `..` lexically without following symlinks, matching the client's path calculation even when a symlink precedes `..` or a component does not exist. Deletion runs only if normalization succeeds. If the tool is missing or rejects these options, install a compatible coreutils tool before retrying. This requirement applies to these shell cleanup recipes.

Deleting the data dir resets the client. It loses the settings, the session key and the Hub password, and on a client with no Hub, what no other place holds: the Local archive's events whose JSONL Claude Code has since pruned, and the Usage history's samples. A Hub keeps its own copies of the events and samples it received. It also loses the machine id, so a Hub sees the next boot as a new machine, and this machine's past usage stays under the old Machine directory entry. To reset only the Local archive, stop the daemon and delete the archive with its `-wal` and `-shm` files. Like the client, this recipe ignores an unset, empty or relative `XDG_DATA_HOME`:

```sh
case "${XDG_DATA_HOME:-}" in
  /*) data_dir="$XDG_DATA_HOME/maxprice" ;;
  *) data_dir="$HOME/.local/share/maxprice" ;;
esac
data_dir=$(realpath -m -s -- "$data_dir") &&
  rm -f -- "$data_dir/local-archive.sqlite" "$data_dir/local-archive.sqlite-wal" "$data_dir/local-archive.sqlite-shm"
```

The next boot fills it again from the JSONL still on disk.

## Uninstalling

```sh
maxprice service uninstall
rm ~/.local/bin/maxprice
```

`service uninstall` stops and disables the unit and removes its file. It keeps the data dir with its secrets.json, the unit's drop-ins in the `maxprice.service.d` dir it names (`~/.config/systemd/user/maxprice.service.d` by default), and linger. Stop any `maxprice serve` running outside the unit, then remove those too if you want them gone: that `.d` dir, `loginctl disable-linger` when nothing else of yours needs it, and the data dir, which deletes everything [the data dir](#the-data-dir) lists, the Local archive included. This recipe also ignores an unset, empty or relative `XDG_DATA_HOME` and requires the `realpath -m -s` support described [above](#the-data-dir):

```sh
case "${XDG_DATA_HOME:-}" in
  /*) data_dir="$XDG_DATA_HOME/maxprice" ;;
  *) data_dir="$HOME/.local/share/maxprice" ;;
esac
data_dir=$(realpath -m -s -- "$data_dir") &&
  rm -r -- "$data_dir"
```

For a system unit, in place of `service uninstall`:

```sh
sudo systemctl disable --now maxprice-dev
sudo rm /etc/systemd/system/maxprice-dev.service
sudo systemctl daemon-reload
```

## Troubleshooting

Start with `maxprice status`: each line that has a fix names the command for it.

| What you see                                                       | What to do                                                                                                                                                                                              |
| ------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `the daemon is not running.` (exit 3)                              | Run the hint it prints: `systemctl --user start maxprice` once the unit is installed, else `maxprice service install` or `maxprice serve`. A shell with another `XDG_DATA_HOME` reaches another daemon  |
| `the daemon is X but this maxprice is Y.` (exit 4)                 | This binary and the daemon differ, as after an install over a running daemon: `systemctl --user restart maxprice`, or restart your `serve`                                                              |
| `the daemon is already running for …`: `serve` exits 5             | Another `maxprice serve` already holds this data dir; use that one                                                                                                                                      |
| `Fix the file, then start the daemon again.`: `serve` exits 6      | It refused `settings.json`, for the reason on the line above. Fix the file, then start it again                                                                                                         |
| The unit failed, or stops when you log out                         | `maxprice service logs -n 100` says why; `maxprice service install` clears a failed state, and `loginctl enable-linger` keeps it running after logout                                                   |
| Every `service` verb exits 1: `no systemd user manager here (…)`   | Run `maxprice serve` under another init; see [Other inits](#other-inits)                                                                                                                                |
| Limits print `—`                                                   | No fresh reading: with no Hub, set the session key with `maxprice key set`, then check the Limits line of `maxprice status`                                                                             |
| A report misses recent sessions                                    | Try `--org all`, check `maxprice settings get claude-paths`, then `maxprice rescan`                                                                                                                     |
| A model shows no cost                                              | `maxprice pricing refresh`, then the Pricing line of `maxprice status`. Under `cost-mode display` a request counts only the cost its log recorded, and current Claude Code records none, so it reads $0 |
| `'alpha' names 2 projects; give its path` (exit 2)                 | Pass the project's path, such as `--project ~/git/alpha`                                                                                                                                                |
| `--machine needs the Fleet replica, which is off here: …` (exit 2) | Join a Hub, and leave `fleet-replica` on                                                                                                                                                                |

## Platform floor

`maxprice` is built by Bun for linux-x64 and links against glibc. In each image below, it ran as a new user other than root, with no network: `maxprice --version`, then `maxprice serve` over a small synthetic set of Claude Code logs, then `maxprice status` against that daemon, and `maxprice daily`, which answered the same totals in every image that ran it. The floor, the oldest glibc where all three pass, is **glibc 2.28** (Rocky Linux 8). No older glibc was tried.

| Image          | glibc       | `--version`                       | `serve`                  | `status` |
| -------------- | ----------- | --------------------------------- | ------------------------ | -------- |
| `ubuntu:20.04` | 2.31        | exit 0                            | scanned; SIGTERM exits 0 | exit 0   |
| `ubuntu:22.04` | 2.35        | exit 0                            | scanned; SIGTERM exits 0 | exit 0   |
| `ubuntu:24.04` | 2.39        | exit 0                            | scanned; SIGTERM exits 0 | exit 0   |
| `debian:11`    | 2.31        | exit 0                            | scanned; SIGTERM exits 0 | exit 0   |
| `debian:12`    | 2.36        | exit 0                            | scanned; SIGTERM exits 0 | exit 0   |
| `rockylinux:8` | 2.28        | exit 0                            | scanned; SIGTERM exits 0 | exit 0   |
| `rockylinux:9` | 2.34        | exit 0                            | scanned; SIGTERM exits 0 | exit 0   |
| `alpine`       | none (musl) | exit 127: the shell's `not found` | not run                  | not run  |

- **musl.** There is no musl build. On Alpine the glibc binary does not start: the kernel finds no glibc loader, and the shell reports `not found`.
- **arm64.** There is no arm64 build: the tarball is x86-64 only.
- **No runtime check.** On a host below the floor the loader fails before any of maxprice's code runs, so the first command fails with the loader's own message.
- **The kernel.** The containers share the host's kernel, so the table says nothing about an older kernel.
- **systemd.** `systemd-analyze verify` reports no problem with the generated unit or the system unit above under systemd 259, as user and system units, or under Rocky Linux 8's systemd 239. The 239 warning about an unknown service type came only from a separate deliberate `Type=bogus` control; neither MaxPrice unit emitted it. With no user manager in a container, 239 parsed the generated unit as a system unit. Neither ran under a manager for this table.
